# Игровые викторины: спецификация для разработки

**Статус:** черновик для продуктового и технического ревью  
**Версия:** 0.3\
**Дата:** 2026-10-09\
**Прототип:** `feature/solo-vocabulary-quiz/flow/`  

Связанные документы: [use cases для ученика и администратора](USE_CASES.md), [план реализации и архитектурные границы](IMPLEMENTATION_PLAN.md), [GAP / журнал реализации](GAP.md). Детальные статусы задач ведутся в разделе 29; оперативная сводка GAP синхронизируется с ним по запросу пользователя.

## 1. Назначение документа

Документ описывает новый формат раздела «Викторины»: каталог готовых игр, универсальную игровую комнату, одиночный и совместный запуск, несколько типов игрового контента и администрирование игр.

После согласования этот документ должен быть основным источником требований для реализации. HTML-макеты задают внешний вид и желаемый сценарий, но при расхождении со спецификацией приоритет имеет спецификация.

Реализация этапа 1 начата. 2026-10-09 пользователь принял пакет рекомендаций §§ 2.1/2.4 плана; контракты foundation зафиксированы в ARCHITECTURE.md. Актуальный ход работ и результаты проверок — в разделе 29 и GAP.md. Согласование контракта не означает готовности реализации.

## 2. Продуктовая идея

Викторина — это готовая игра, а не конструктор, который ученик собирает перед каждым запуском.

На странице «Викторины» ученик сразу видит карточки игр, например:

- «English: перевод слов»;
- «Қазақша сөздер»;
- «Математика, 5 класс»;
- «Удивительные факты: верю / не верю».

Нажатие на карточку открывает комнату конкретной игры. Комната создаётся всегда, даже если ученик собирается играть один. Организатор может:

- сразу запустить игру в одиночку;
- показать код комнаты, пригласить других учеников и дождаться их готовности;
- при необходимости выбрать разрешённые игрой настройки, например класс.

Не должно быть предварительной вложенной навигации вида «Викторины → Слова → Английский → Играть».

## 3. Цели

1. Сократить путь от раздела «Викторины» до начала игры до двух обязательных действий: выбрать игру и нажать «Начать игру».
2. Использовать одну модель комнаты и один игровой жизненный цикл для одиночной и совместной игры.
3. Поддержать разные типы игр без обязательного предмета или класса.
4. Не показывать детям неподходящий по возрасту или программе контент.
5. Дать администратору управляемый процесс создания, проверки и публикации игр и контента.
6. Сохранить текущий визуальный язык, серверный рендеринг Thymeleaf и существующую архитектуру Spring Boot.
7. Обеспечить воспроизводимость результата: изменение банка после старта не должно менять уже начатую или завершённую игру.

## 4. Не входит в первую версию

- генерация слов, переводов, утверждений или дистракторов моделью во время игры;
- пользовательский конструктор игр для учеников;
- голосовой чат, текстовый чат и модерация сообщений;
- команды и командный режим;
- вход в уже начавшуюся игру;
- интервальное повторение и отдельная модель «выученности» слова;
- призы, внутренняя валюта, серии дней и магазин;
- влияние скорости ответа на количество баллов;
- загрузка аудио и автоматическая проверка произношения;
- полностью универсальный JSON-конструктор неизвестных будущих типов контента.

Эти возможности могут быть добавлены позднее, но первая версия не должна заранее усложняться ради них.

## 5. Термины

| Термин | Значение |
| --- | --- |
| Игра | Опубликованная карточка в каталоге с типом, оформлением, правилами и источником контента. |
| Версия игры | Неизменяемый опубликованный набор настроек игры. Новое редактирование создаёт новый черновик. |
| Комната | Экземпляр запуска игры. Существует и для одного участника. |
| Организатор | Ученик, создавший комнату. Только он запускает и отменяет игру. |
| Участник | Ученик, находящийся в комнате. Организатор также является участником. |
| Банк | Курируемый набор опубликованных материалов одного типа. |
| Раунд | Один вопрос, слово или утверждение внутри запущенной комнаты. |
| Снимок раунда | Текст, варианты и правильный ответ, сохранённые при старте комнаты. |
| Политика класса | Правило, определяющее, выбирает ли ученик класс перед игрой. |
| Аудитория контента | Независимое правило безопасности, определяющее, для каких классов допустим материал. |

## 6. Базовые продуктовые решения

### 6.1. Каталог вместо дерева категорий

Главная страница раздела показывает готовые игры. Категории и фильтры могут помогать поиску, но не создают обязательных дополнительных экранов.

Карточка игры должна содержать:

- локализованное название;
- короткое описание в одну строку;
- понятный тип или механику;
- длительность или количество раундов;
- количество возможных игроков;
- признак необходимости выбрать класс, если это требуется;
- основное действие «Играть».

Весь объект карточки кликабелен. Отдельная кнопка может визуально повторять действие, но не должна вести в другой сценарий.

Редакционная публикация, административная видимость в каталоге и доступность конкретному ученику — независимые проверки. Администратор может скрыть опубликованную карточку без архивирования и потери версии/истории, затем вернуть её. Каталог не показывает скрытую карточку; новые create/replay, включая прямой POST, запрещены. Ранее созданная WAITING-комната может принимать гостей и стартовать при остальных финальных проверках. Скрытие не прерывает ACTIVE и не лишает исторического результата; архивация отдельно блокирует новый старт. Изменение видимости аудируется (DEC-05, принято 2026-10-09).

### 6.2. Комната существует всегда

После выбора игры сервер создаёт комнату со статусом `WAITING`. Организатор автоматически добавляется участником и считается готовым.

Код комнаты генерируется сразу и хранится в базе. В интерфейсе его можно не акцентировать, пока организатор не нажал «Пригласить», но отдельной ленивой генерации кода не требуется.

### 6.3. Одиночная игра — не отдельный режим данных

Если в комнате только организатор, он может нажать «Начать игру». Это обычная комната с одним участником, а не отдельная таблица сессий и не другой игровой движок.

### 6.4. Совместная игра

Организатор показывает или копирует код. Другой ученик вводит код, видит название игры и присоединяется к комнате.

Новый участник получает статус «Ожидает» и один раз нажимает «Готов». Это осознанное подтверждение участия и единственный дополнительный шаг гостя. Организатор не может запустить игру, пока хотя бы один присоединившийся участник не готов.

После старта присоединение запрещено.

### 6.5. Подтверждение запуска

Экран комнаты сам является подтверждением «Запускаем игру?». Нажатие организатором «Начать игру» запускает игру сразу; дополнительное модальное окно не показывается.

Перед кнопкой должны быть видны:

- название и краткие правила;
- количество вопросов и время на вопрос;
- участники и их готовность;
- выбранный класс, если он влияет на игру;
- доступность контента либо понятная причина, почему запуск пока невозможен.

## 7. Поддерживаемые типы игр

### 7.1. `WORD_TRANSLATION` — перевод слов

Пример: вопрос на английском, четыре варианта перевода на русском.

Обязательные свойства:

- исходный и целевой языки;
- ссылка на опубликованный словарный набор;
- один правильный вариант и три однозначных дистрактора;
- неизменяемый снимок слова и показанных вариантов при старте;
- отсутствие генерации контента в момент игры.

Поддерживаемые направления первой версии:

- `en → ru`;
- `kk → ru`;
- `ru → kk`, если для направления создан и опубликован отдельный набор.

Направление задаётся игрой и не переключается учеником внутри комнаты.

### 7.2. `SUBJECT_QUIZ` — предметная викторина

Использует существующий банк опубликованных версий вопросов. Игра задаёт предмет, допустимые типы вопросов, сложность и политику класса.

В первой версии сохраняются существующие типы вопросов:

- `SCQ`;
- `MCQ`;
- `MATCHING`;
- `FILL_IN`.

### 7.3. `TRUE_FALSE` — верю / не верю

Показывает утверждение и два действия: «Верю» и «Не верю». Класс не обязан отображаться или выбираться.

Для этого типа используется отдельный курируемый банк утверждений. Не следует маскировать его под предмет `SCQ` с фиктивным предметом «Общие знания»: это создаёт неверную предметную модель и усложняет редактуру.

У утверждения должны храниться:

- текст на поддерживаемых языках интерфейса;
- истинность;
- короткое объяснение для разбора результата;
- проверяемый источник;
- допустимая аудитория;
- статус редакционной проверки.

### 7.4. Матрица различий

| Свойство | WORD_TRANSLATION | SUBJECT_QUIZ | TRUE_FALSE |
| --- | --- | --- | --- |
| Источник | Словарный набор | Банк вопросов | Банк утверждений |
| Предмет обязателен | Нет | Да | Нет |
| Выбор класса | Зависит от игры | Обычно да | Обычно нет |
| Варианты | 4 перевода | По типу вопроса | 2 фиксированных ответа |
| Объяснение после игры | Значение/примечание | Существующее объяснение | Обоснование и источник |
| Контент генерируется при старте | Нет | Нет | Нет |

## 8. Класс и безопасность аудитории

Выбор класса в интерфейсе и возрастная допустимость контента — разные задачи. Они не должны управляться одним флагом.

### 8.1. Политика выбора класса `grade_selection_mode`

| Значение | Поведение комнаты |
| --- | --- |
| `NONE` | Поле класса отсутствует. |
| `PROFILE_DEFAULT` | Класс заполняется из профиля организатора и может быть изменён на разрешённый. |
| `REQUIRED` | Организатор обязан выбрать один из разрешённых классов. Без выбора запуск недоступен. |

### 8.2. Политика аудитории `audience_policy`

| Значение | Правило выборки контента |
| --- | --- |
| `UNIVERSAL` | Разрешён только контент, явно проверенный для всех поддерживаемых школьных классов. |
| `PARTICIPANT_GRADES` | Материал обязан быть допустим для классов всех участников; поле класса в комнате не показывается. |
| `ROOM_GRADE` | Используется класс, выбранный в комнате. Допустимо только при `PROFILE_DEFAULT` или `REQUIRED`. |
| `FIXED_GRADES` | Игра доступна только ученикам из настроенного списка классов; материал дополнительно проверяется по фактическим классам участников. |

Это разделение позволяет, например, не показывать выбор класса в простой игре со словами, но всё равно подобрать слова, разрешённые для каждого участника комнаты. Старший организатор не должен приводить младшего гостя к контенту, который разрешён только старшим классам.

В текущем профиле ученика есть `gradeNo`, но нет даты рождения или возраста. Поэтому первая версия не может автоматически подбирать контент по возрасту. Поле «10–12 лет» в макете следует считать редакционной подсказкой, а не исполняемым правилом. Исполняемая граница первой версии — класс.

Если политика требует классы профилей, а класс не указан хотя бы у одного участника, присоединение или старт блокируется с понятным сообщением и ссылкой на профиль. Система не подставляет более взрослый или случайный материал.

Для `PARTICIPANT_GRADES` материал подходит, только если его список разрешённых классов содержит класс каждого участника. Для `ROOM_GRADE` младший ученик не может присоединиться к комнате более старшего класса; ученик старшего класса может играть в материал младшего класса. Универсальный материал подходит всем участникам.

## 9. Пользовательские сценарии

### 9.1. Открытие каталога

1. Ученик открывает `/student/quiz`.
2. Сервер возвращает опубликованные игры, разрешённые для показа роли ученика, и отдельно рассчитывает доступность запуска.
3. Игры сортируются по административному порядку, затем по названию.
4. Недоступная из-за неполного профиля игра либо скрывается, либо показывается заблокированной только когда причина устранима учеником. Для первой версии предпочтительно показывать заблокированную карточку с причиной.
5. Если опубликованных игр нет, показывается пустое состояние без технических терминов.

### 9.2. Создание комнаты

1. Ученик нажимает карточку.
2. Сервер проверяет статус игры и доступ ученика.
3. Создаётся `WAITING`-комната, связанная с конкретной опубликованной версией игры.
4. Генерируется уникальный код.
5. Организатор добавляется участником с `ready = true`.
6. Раунды на этом этапе не создаются: финальная выборка контента выполняется атомарно при старте.
7. Ученик перенаправляется на страницу комнаты.

Повторная отправка формы из-за двойного клика не должна создавать две комнаты. Для создания применяется одноразовый токен формы или idempotency key.

### 9.3. Запуск в одиночку

1. Организатор проверяет параметры.
2. Нажимает «Начать игру».
3. Сервер повторно проверяет игру, аудиторию и количество доступного опубликованного контента.
4. В одной транзакции создаёт снимки раундов и переводит комнату в `ACTIVE`.
5. Клиент открывает первый раунд.

### 9.4. Приглашение

1. Организатор нажимает «Пригласить».
2. Интерфейс показывает код и действие «Скопировать».
3. Копируется короткий код и, если доступно, полная ссылка на вход.
4. Комната остаётся `WAITING`.

### 9.5. Вход по коду

1. Ученик открывает форму входа и вводит код без учёта регистра и пробелов по краям.
2. Сервер нормализует код и проверяет комнату.
3. До присоединения показываются название игры, организатор, число участников и правила.
4. После подтверждения ученик добавляется с `ready = false`.
5. Ученик нажимает «Готов» и ожидает организатора.

Нельзя присоединиться, если комната не найдена, истекла, заполнена, отменена или уже запущена. Каждая причина имеет отдельное пользовательское сообщение.

Нормализация кода — удаление пробелов по краям и приведение к каноническому регистру без зависимости от локали. Внутренние пробелы и неподдерживаемые символы дают ошибку валидации, не исправляются в другой код автоматически. Одно правило применяется в preview, join, комнатных HTTP-маршрутах и авторизации WebSocket topic. Ограничение длины и допустимый алфавит согласуются с генератором и историческими кодами.

### 9.6. Старт с друзьями

Организатор может стартовать, если:

- комната находится в `WAITING`;
- он остаётся участником комнаты;
- все остальные участники готовы;
- число участников не превышает лимит;
- настройки валидны;
- опубликованного контента достаточно.

Двойной запрос старта должен создать раунды один раз. Конкурирующие запросы блокируются на строке комнаты или атомарным переходом статуса.

### 9.7. Игровой раунд

- Все участники получают одинаковый снимок раундов и одинаковый порядок.
- Время раунда рассчитывается от серверного `startedAt`, номера раунда и `roundSeconds`.
- Клиентский таймер только отображает серверное время и не является источником истины.
- Текст и варианты будущих раундов не передаются клиенту до начала соответствующего раунда.
- До завершения комнаты клиент не получает правильный ответ, признак правильности варианта или объяснение.
- После принятого ответа элементы выбора блокируются.
- Если время истекло без ответа, сервер фиксирует ответ как пропущенный с нулём баллов.
- Краткий сетевой сбой не останавливает серверный таймер. После восстановления клиент перечитывает состояние комнаты.

В первой версии за правильный ответ начисляется один балл независимо от скорости. Таймер создаёт ограничение времени, но не даёт бонусных баллов.

### 9.8. Результат

После последнего раунда комната переводится в `FINISHED`. Результат содержит:

- место участника;
- число правильных ответов;
- общее число раундов;
- процент;
- разбор собственных ответов;
- правильный ответ и объяснение;
- действие «Сыграть ещё раз», создающее новую комнату той же опубликованной версии либо актуальной версии игры — решение ниже.

Принятое правило: «Сыграть ещё раз» использует актуальную опубликованную версию игры. История завершённой комнаты остаётся связанной со старой версией.

Сортировка результата: количество баллов по убыванию, затем суммарное время по всем раундам по возрастанию, затем время входа в комнату. Для пропущенного раунда в сумму записывается полный лимит раунда. Скорость используется только как разрешение ничьей, а не как бонус к баллам.

Полный лимит применяется и к явному пропуску, и к серверному тайм-ауту. Раннее нажатие «Пропустить» не улучшает место; пропуск окончателен и даёт ноль баллов. Булево `false` — содержательный ответ в игре фактов, не признак отсутствия ответа. Payload/хранение закреплены в ARCHITECTURE.md; правило подсчёта уже определено.

ARCH-01 закрыт: ID текущего раунда и либо typed answer, либо skipped=true, не оба; explicit skipped/timed_out сохраняются отдельно. Окно ответа `[roundStart, roundEnd)`, без late grace для новых игр; подробности — ARCHITECTURE.md.

### 9.9. Выход и отмена

- Гость может покинуть только `WAITING`-комнату; его запись участника удаляется.
- Организатор в `WAITING` не «покидает», а отменяет комнату. Статус становится `CANCELLED`.
- Выход со страницы во время `ACTIVE` не удаляет участника и не останавливает игру. Сервер завершает его пропущенные раунды по тайм-ауту.
- Возврат участника по тому же аккаунту в активную комнату восстанавливает экран текущего раунда.

## 10. Состояния и жизненный цикл комнаты

| Статус | Назначение | Допустимые переходы |
| --- | --- | --- |
| `WAITING` | Настройка и ожидание участников | `ACTIVE`, `CANCELLED`, `EXPIRED` |
| `ACTIVE` | Идут раунды | `FINISHED` |
| `FINISHED` | Результат рассчитан | Конечное состояние |
| `CANCELLED` | Организатор отменил запуск | Конечное состояние |
| `EXPIRED` | Комната не стартовала до срока | Конечное состояние |

Ожидающая комната истекает через 30 минут после создания. Время должно быть конфигурируемым. Фоновая задача отмечает её `EXPIRED`, но не удаляет историю физически.

Для активной комнаты плановое время окончания вычисляется из количества раундов и длительности. Существующий серверный обработчик тайм-аутов расширяется, а не заменяется клиентской логикой.

### 11.1. Список игр

Показывает:

- стабильный код;
- тип;
- статус;
- источник контента;

### 11.2. Создание и редактирование игры

Поля общей части:

- стабильный `code`, меняется только до первой публикации;
- тип игры, меняется только до первой публикации;
- название и описание на русском и казахском;
- подпись механики для карточки;
- порядок в каталоге;
- визуальный вариант из ограниченного набора существующих стилей;
- количество раундов по умолчанию, минимум и максимум;
- секунд на раунд по умолчанию, минимум и максимум;
- максимальное число участников, от 1 до 4 в первой версии;
- `grade_selection_mode`;
- `audience_policy`;
- разрешённые классы, когда они нужны выбранным политикам;
- источник контента;
- состояние видимости в каталоге.

Типоспецифичные поля:

- `WORD_TRANSLATION`: словарный набор и направление перевода;
- `SUBJECT_QUIZ`: предмет, допустимые типы вопроса, сложность;
- `TRUE_FALSE`: набор утверждений.

После первой публикации редактирование создаёт новую черновую версию. Опубликованная версия продолжает обслуживать уже созданные комнаты.

Управление видимостью опубликованной карточки — отдельное действие, не перевод в DRAFT/ARCHIVED. Форма/список различают опубликованную версию, новый черновик и скрытие. Поле catalog_visible и audit изменения находятся на стабильной игре; изменение работает без новой редакции учебного контента. Команда административного POST реализуется в GAME-09, не в foundation.

### 11.3. Контент игры

Страница должна не копировать материалы внутрь игры, а показывать связанный банк и результат фильтрации:

- сколько материалов опубликовано;
- сколько подходит аудитории;
- сколько может участвовать в игре с текущими правилами;
- почему конкретный материал исключён;
- достаточно ли материалов для максимального числа раундов;
- есть ли неоднозначные ответы или недостающие переводы.

Для `SUBJECT_QUIZ` ссылка ведёт к существующему банку вопросов с предустановленными фильтрами. Для слов и утверждений используются отдельные страницы банка.

### 11.4. Банк слов

Список слов поддерживает:

- фильтр по набору, языковой паре, классу, статусу и сложности;
- поиск по исходному слову и переводам;
- отображение источника;
- массовую отправку на проверку;
- архивирование без физического удаления опубликованной истории;
- предупреждение о дублях и неоднозначных вариантах.

Карточка слова содержит:

- исходное слово;
- нормализованную форму для поиска дублей;
- транскрипцию;
- часть речи;
- одно конкретное учебное значение;
- основной перевод;
- допустимые альтернативные переводы;
- примечание для разбора;
- сложность;
- ссылку на проверяемый источник;
- классы или признак универсальной аудитории;
- редакционный статус;
- автора и проверяющего.

Если слово многозначное, каждое учебное значение создаётся отдельной записью. Нельзя объединять несовместимые значения в один вопрос.

Редакционная готовность слова и пригодность для игрового вопроса различаются. Публикация версии слова проверяет значение, один основной перевод, альтернативы, источник, аудиторию и статус проверки; не требует уже иметь три других опубликованных слова-дистрактора. Иначе пустой банк нельзя наполнить. Возможность построить четыре однозначных варианта проверяется диагностикой, публикацией игры и финальным стартом; непригодное слово не используется как игровой вопрос. У набора явно различаются опубликованность и достаточность пригодного наполнения для конкретной игры.

### 11.5. Банк утверждений

Карточка утверждения содержит:

- текст на русском и казахском;
- правильное булево значение;
- короткое объяснение;
- проверяемый источник;
- классы или признак универсальной аудитории;
- статус;
- автора и проверяющего.

Одного URL без объяснения недостаточно для публикации. Редактор должен понимать, какой именно факт подтверждает источник.

### 11.6. Редакционные статусы

Для игр и новых банков применяется единый понятный жизненный цикл:

| Статус | Значение |
| --- | --- |
| `DRAFT` | Редактируется, ученикам недоступно. |
| `NEEDS_REVIEW` | Автор закончил работу, ожидается проверка. |
| `APPROVED` | Проверено, но ещё не опубликовано. |
| `PUBLISHED` | Доступно игровому движку. |
| `ARCHIVED` | Не используется в новых играх, но сохраняется в истории. |

Самопроверка конфигурируется; для MVP строгий запрет по умолчанию выключен. При включённом запрете автор не может утвердить собственный материал. Поля автора, проверяющего и времени сохраняются независимо от этого флага (DEC-01, принято 2026-10-09).

### 11.7. Проверка перед публикацией игры

Публикация блокируется, если:

- отсутствует перевод обязательного названия;
- неверны ограничения количества раундов или времени;
- политика класса несовместима с политикой аудитории;
- источник контента не опубликован;
- подходящих материалов меньше минимального количества раундов;
- для слов нельзя построить четыре однозначных варианта;
- у утверждений отсутствуют объяснение или источник;
- опубликованный состав источника/выборки содержит неподтверждённые материалы; отдельные неопубликованные черновики не блокируют пригодную проверенную публикацию;
- максимальное число игроков меньше одного или больше четырёх.

Страница проверки показывает ошибки, предупреждения и точные ссылки для исправления. Кнопка «Опубликовать» доступна только при отсутствии ошибок. Предупреждения не блокируют публикацию, но требуют осознанного подтверждения.

## 12. Правила формирования контента

### 12.1. Общие правила

При старте сервер:

1. Загружает опубликованную версию игры.
2. Разрешает исполняемый класс аудитории.
3. Получает только опубликованные материалы подходящего банка и аудитории.
4. Исключает материалы, уже выбранные в эту комнату.
5. Случайно выбирает нужное количество на сервере.
6. Для каждого раунда строит и перемешивает варианты.
7. Сохраняет снимки раундов.
8. Только после успешного сохранения переводит комнату в `ACTIVE`.

Если материалов недостаточно, транзакция не создаёт частичный набор раундов, комната остаётся `WAITING`, а организатор получает ошибку `INSUFFICIENT_PUBLISHED_CONTENT` с доступным и необходимым количеством.

Выборка должна быть случайной, но не обязана использовать `ORDER BY random()` на всей таблице. Допустимая реализация первой версии: получить ограниченный набор подходящих идентификаторов, перемешать в Java и выбрать первые N. Криптографическая случайность не требуется.

### 12.2. Слова и дистракторы

В игровой вопрос попадают только материалы, для которых:

- набор и версия слова опубликованы;
- языковое направление совпадает с игрой;
- аудитория допускает исполняемый класс;
- есть ровно один основной перевод;
- все варианты принадлежат тому же направлению и совместимой аудитории;
- ни один дистрактор не совпадает с основным или допустимым альтернативным переводом;
- редактор не запретил пару как синонимичную или двусмысленную;
- после фильтрации остаётся не менее трёх дистракторов.

Предпочтительный подбор дистракторов:

1. та же часть речи;
2. близкая сложность;
3. тот же набор;
4. при нехватке — другой опубликованный набор той же языковой пары и аудитории, если администратор явно разрешил межнаборный подбор.

По умолчанию межнаборный подбор выключен.

### 12.3. Предметные вопросы

Используются только `QuestionVersion` со статусом `PUBLISHED`, соответствующие предмету, классу, языку, сложности и разрешённому типу. Одна версия вопроса не повторяется внутри комнаты.

Существующий `AnswerChecker` сохраняется для предметных вопросов. Новые типы контента проверяются отдельными адаптерами игрового раунда, а не искусственными `QuestionVersion`.

### 12.4. Утверждения

Выбираются только опубликованные версии с подтверждённым источником и подходящей аудиторией. В снимке раунда сохраняются текст, правильное значение и объяснение.

Ответ клиента передаётся как булево значение. Строковые варианты «Да», «Нет», «Верю» и «Не верю» не являются значениями протокола и могут локализоваться без изменения проверки.

### 13.1. Игры

#### `quiz_games`

Стабильная сущность игры:

Неизменяемая опубликованная конфигурация и изменяемый черновик до публикации:

| Поле | Назначение |
| --- | --- |
| `id`, `game_id`, `version_no` | Идентификация версии |

| `round_seconds_editable` | Может ли организатор менять таймер в пределах границ |

### 13.2. Словарный банк

#### `vocabulary_sets`

Содержит стабильный код, языковую пару, локализованные названия, редакционный статус, источник, признак разрешения межнаборных дистракторов и аудит.

#### `vocabulary_set_versions`

Фиксирует опубликованную версию общих настроек набора. Набор отдельно хранит ссылки на опубликованную и черновую версии по тому же правилу, что и игра.

#### `vocabulary_items`

Стабильная сущность одного значения слова: `id`, `set_id`, `status`, `published_version_id`, `draft_version_id`, аудит.

#### `vocabulary_item_versions`

| Поле | Назначение |
| --- | --- |
| `item_id`, `version_no` | Версия |
| `source_text`, `source_normalized` | Показываемое и нормализованное слово |
| `pronunciation` | Транскрипция, nullable |
| `part_of_speech` | Часть речи, nullable |
| `meaning_note_ru`, `meaning_note_kk` | Одно учебное значение и разбор |
| `difficulty` | 1–5 |
| `source_reference` | Проверяемый источник |
| `created_by`, `reviewed_by`, timestamps | Аудит |

#### `vocabulary_item_answers`

Привязаны к версии слова, содержат текст, нормализованный текст и `is_primary`. Для версии допускается ровно один основной ответ и несколько допустимых альтернатив.

#### `vocabulary_item_grades`

Связывает версию слова с допустимыми классами. Для универсального материала используется явный признак `universal_audience`, а не отсутствие связей: пустой список не должен двусмысленно означать «для всех» или «ни для кого».

#### `vocabulary_distractor_exclusions`

Хранит запрещённые пары версий слов и редакционную причину.

### 13.3. Банк утверждений

#### `fact_sets`

Стабильный тематический набор со статусом, названиями, источниковой политикой и аудитом.

#### `fact_statements` и `fact_statement_versions`

Версия содержит локализованный текст, `truth_value`, локализованное объяснение, `source_reference`, `universal_audience`, автора и проверяющего.

`fact_statements` хранит отдельные ссылки на опубликованную и черновую версии; опубликованная версия после публикации неизменяема.

#### `fact_statement_grades`

Необязательные допустимые классы для неуниверсального утверждения.

### 13.4. Расширение комнат

К существующей `quiz_rooms` добавляются:

| Поле | Назначение |

| `expires_at` | Время истечения ожидания |
| `cancelled_at` | Время отмены, nullable |

Существующие `subject_id`, `grade_id`, `language`, `difficulty`, `question_count`, `round_seconds`, `max_players` сохраняются на первом этапе ради совместимости и снимка настроек. Для новых комнат их значения вычисляются из версии игры и допустимых пользовательских настроек.

`game_version_id` сначала добавляется nullable для совместимости с историческими строками. Для всех новых комнат сервис обязан записывать его; после миграции или истечения старых активных комнат можно добавить ограничение.

Статусы расширяются значениями `CANCELLED` и `EXPIRED`.

Для снимка фактической аудитории добавляется `quiz_room_audience_grades(room_id, grade_no)`. При старте туда записываются уникальные классы участников для `PARTICIPANT_GRADES` и `FIXED_GRADES`. История комнаты после этого не зависит от изменения профилей.

### 13.5. Расширение раундов

Текущий обязательный `quiz_rounds.question_version_id` недостаточен. Он становится nullable, а раунд получает:

| Поле | Назначение |
| --- | --- |
| `content_kind` | `QUESTION`, `VOCABULARY`, `FACT` |
| `question_version_id` | Источник предметного вопроса, nullable |
| `vocabulary_item_version_id` | Источник слова, nullable |
| `fact_statement_version_id` | Источник утверждения, nullable |
| `prompt_snapshot` | Локализованный показанный текст |
| `options_snapshot_json` | Упорядоченные варианты без признака правильности |
| `answer_key_snapshot_json` | Правильный ответ, никогда не отдаётся до результата |
| `explanation_snapshot` | Разбор после завершения |

Проверочное ограничение базы требует ровно одну ссылку-источник, соответствующую `content_kind`.

JSON здесь допустим как неизменяемый снимок уже сформированного раунда, а не как редактируемая доменная модель.

### 13.6. Ответы и результаты

К `quiz_answers` добавляются:

- `response_ms` — время от начала раунда до принятия ответа;
- `timed_out` — явный признак серверного пропуска по времени.

Уникальность `(round_id, participant_id)` сохраняется.

Первый принятый содержательный ответ или явный пропуск является финальным. Повтор того же запроса возвращает текущее состояние идемпотентно; попытка заменить ответ другим значением или заменить принятый пропуск ответом возвращает конфликт. Серверный тайм-аут создаёт пустой ответ только если нет ни принятого ответа, ни явного пропуска; тайм-аут не перезаписывает их.

Текущая возможность менять сохранённый ответ до конца раунда должна быть удалена из UI и сервиса для новых игр. Для старого режима на переходный период возможен отдельный совместимый флаг, но целевое правило едино.

## 14. Серверные компоненты

Рекомендуемое разделение ответственности:

- `QuizGameCatalogService` — доступные игры и локализация карточек;
- `QuizGameAdminService` — черновики, валидация и публикация игр;
- `QuizRoomService` — жизненный цикл комнаты, участники и права;
- `QuizRoundFactory` — общий оркестратор формирования раундов;
- `SubjectRoundProvider` — существующие вопросы;
- `VocabularyRoundProvider` — слова и дистракторы;
- `FactRoundProvider` — утверждения;

Точные DTO могут уточняться при реализации, но поведение и права ниже обязательны.

Существующий формат создания по `subjectId` и `gradeId` временно сохраняется как устаревший для старой страницы. Новый интерфейс его не использует. Срок удаления назначается после миграции всех предметных игр в каталог.

### 15.3. Состояние комнаты

Текущий `QuizRoomResponse` расширяется, а существующие поля не переименовываются в первой миграции. Добавляются:

- `gameId`, `gameCode`, `gameType`;
- локализованные `gameTitle`, `gameDescription`;
- `currentParticipantHost`;
- `canStart`, `startBlockers[]`;
- `canInvite`;
- `expiresAt`;
- для раунда — `contentKind`, локализованный снимок и варианты.

До `FINISHED` ответ не содержит `answerKey`, `correctOption`, `isCorrect` для ещё не раскрытого раунда или объяснение, позволяющее вывести правильный ответ. Для будущих раундов возвращаются только номер и временные границы; текст и варианты появляются после `startsAt`.

## 16. События и обновление комнаты

Сохраняется текущая схема WebSocket/STOMP:

- endpoint: `/ws/quiz`;
- topic комнаты: `/topic/quiz.rooms.{code}`.

Событие сообщает тип изменения и идентификатор комнаты, после чего клиент перечитывает состояние через HTTP. Ответы и ключи не отправляются в событии.

Минимальные типы событий:

- `room.participant_joined`;
- `room.participant_left`;
- `room.readiness_changed`;
- `room.started`;
- `room.round_changed`;
- `room.finished`;
- `room.cancelled`;
- `room.expired`.

Периодический HTTP polling остаётся резервом при недоступном WebSocket. Интервал текущей реализации в три секунды приемлем для первой версии.

## 17. Ошибки и пользовательские сообщения

API возвращает стабильный машинный `code`, локализуемое сообщение и, где нужно, безопасные детали.

| Код | HTTP | Сообщение/поведение |
| --- | --- | --- |
| `GAME_NOT_FOUND` | 404 | Игра недоступна или снята с публикации |
| `ROOM_NOT_FOUND` | 404 | Проверьте код комнаты |
| `ROOM_EXPIRED` | 410 | Срок ожидания истёк, создайте новую комнату |
| `ROOM_CANCELLED` | 410 | Организатор отменил игру |
| `ROOM_ALREADY_STARTED` | 409 | Игра уже началась, вход закрыт |
| `ROOM_FULL` | 409 | В комнате нет свободных мест |
| `PARTICIPANT_NOT_READY` | 409 | Показать, кто ещё не готов |
| `HOST_ONLY_ACTION` | 403 | Действие доступно организатору |
| `INVALID_GRADE` | 422 | Выберите разрешённый класс |
| `PROFILE_GRADE_REQUIRED` | 422 | Укажите класс в профиле |
| `INSUFFICIENT_PUBLISHED_CONTENT` | 409 | Недостаточно проверенных материалов; запуск не выполнен |
| `ROUND_NOT_ACTIVE` | 409 | Этот раунд ещё не начался или уже завершён |
| `ANSWER_ALREADY_SUBMITTED` | 409 | Ответ уже зафиксирован |
| `GAME_CONFIGURATION_INVALID` | 409 | Игра временно недоступна; сообщение ученику без внутренних деталей |
| `IDEMPOTENCY_CONFLICT` | 409 | Ключ create уже использован с другими параметрами |
| `SETTINGS_REVISION_CONFLICT` | 409 | Настройки изменились; перечитать состояние перед ready/settings |
| `SETTINGS_INVALID` | 422 | Значения не разрешены опубликованной версией |
| `PARTICIPANT_REQUIRED` | 403 | Полное состояние и результаты доступны только участнику |
| `GUEST_ONLY_ACTION` | 403 | Организатор отменяет комнату вместо leave |
| `RESULTS_NOT_AVAILABLE` | 409 | Разбор появится после FINISHED |
| `ROOM_CODE_INVALID` | 400 | Неподдерживаемый код; внутренние пробелы не исправляются |
| `REQUEST_INVALID` / `ANSWER_INVALID` | 400 | Неверный тип/состав запроса; отсутствие ответа не означает false |
| `ROOM_BUSY` / `ROOM_CODE_EXHAUSTED` | 503 | Повторить запрос после исчерпания ограниченных транзакционных попыток |

Трассировка и логи могут содержать внутреннюю причину, но ученик не должен видеть SQL, идентификаторы версий или стек исключения.

## 18. Безопасность и целостность

1. Все ученические игровые маршруты доступны только роли `STUDENT`.
2. Все административные маршруты доступны только роли `ADMIN`.
3. Родитель и посторонний ученик не могут читать полное состояние комнаты, ответы или результаты до присоединения. Аутентифицированному ученику разрешено только превью: название игры, организатор, число занятых мест, лимит и статус доступности входа.
4. Только организатор запускает и отменяет комнату.
5. Сервер проверяет членство для каждого ответа и чтения состояния.
6. CSRF обязателен для изменяющих браузерных запросов.
7. Код комнаты не даёт доступа без аутентификации ученика.
8. Тексты администратора выводятся с экранированием. Разрешённый HTML вопросов очищается существующим серверным механизмом.
9. Ключ ответа не попадает в DOM скрытым полем, HTML-комментарием, WebSocket-событием или JSON до разрешённого разбора.
10. Все ограничения времени и баллы рассчитываются сервером.
11. Нормализация слов применяется для поиска дублей, но показываемый текст хранится отдельно.
12. Физическое удаление опубликованных версий, участвовавших в комнате, запрещено внешними ключами или сервисным правилом.

Код комнаты текущего формата `QZ` и четыре символа можно сохранить для совместимости. При заметном росте числа одновременных ожидающих комнат длину следует увеличить; генератор обязан повторять попытку при уникальном конфликте. Повтор выполняется с новым кодом и корректной транзакционной границей: нельзя продолжать запрос в уже откатившейся PostgreSQL-транзакции или дублировать host. Число попыток ограничено; исчерпание возвращает безопасную ошибку без частичной комнаты. Тест обязан искусственно воспроизвести коллизию, а не рассчитывать на случайное её появление.

### 18.1. Авторизация WebSocket / STOMP

- Соединение использует аутентифицированного пользователя; проверяется допустимый Origin по политике приложения. HTTP-доступ к endpoint сам по себе не авторизует подписку.
- `SUBSCRIBE /topic/quiz.rooms.{code}` разрешён только роли STUDENT и действующему участнику этой комнаты. Код/topic нормализуется и валидируется; wildcard-подписки и произвольные назначения не должны обходить проверку. PARENT, ADMIN без STUDENT и посторонний ученик не получают комнатный поток.
- Клиент не может публиковать серверные комнатные события через SEND. Изменения игры идут через защищённые HTTP-команды; возможные STOMP-команды отдельно проверяются или запрещаются.
- После успешного leave в WAITING все подписки вышедшего пользователя на комнату, включая другие вкладки, теряют доступ. Отзыв применяется до доставки последующих событий; простого запрета новых SUBSCRIBE недостаточно. При повторном join/соединении права проверяются заново.
- Механизм — входная проверка подписок и отзыв/проверка перед доставкой — фиксируется в `ARCH-01`. Если существующий broker не обеспечивает это, добавляется необходимая защита или используется авторизованный HTTP polling; отсутствие механизма не ослабляет требование.
- Security-тесты: неавторизованный клиент, чужая комната, родитель, wildcard, forged SEND, leave при нескольких вкладках, reconnect после выхода. Секреты и персональные ответы не включаются в общие события даже для участников.

## 19. Локализация и доступность

Решение пользователя 2026-10-11: обязательный ручной речевой проход скринридером
исключён из приёмки текущей поставки. Речь не проверялась и не объявляется проверенной.
Клавиатура, фокус, семантическая разметка, мобильная ширина и reduced motion сохраняются.
Правила live region ниже описывают реализованное поведение; речевая проверка не блокирует выпуск.

- Язык интерфейса определяется существующими настройками пользователя.
- Название и описание игры имеют русскую и казахскую версии.
- Английское слово не переводится как элемент интерфейса; направление языка задаёт контент.
- Кнопки не различаются только цветом: содержат текст и видимый focus state.
- Выбор ответа доступен с клавиатуры.
- Таймер имеет текстовое значение и не озвучивается каждую секунду screen reader. Объявляются только пороги, например 10 и 5 секунд.
- После отправки фокус переходит на статус ответа, после смены раунда — на заголовок нового вопроса.
- Минимальная сенсорная область — 44×44 CSS px.
- Анимации учитывают `prefers-reduced-motion`.
- Ошибка связывается с полем через `aria-describedby`, а не обозначается одним красным цветом.

Fallback карточек/необязательного метатекста: локаль пользователя → русский → другая имеющаяся локализация; blank равно отсутствию. Если обязательного заголовка нет нигде, игра безопасно недоступна с диагностикой администратору, без сырого ключа. Fallback не отменяет обязательность переводов публикации и не подменяет учебный материал вопросом другого языка/источника. SSR/JSON используют одну политику (DEC-06, принято 2026-10-09). Live region обновляет таймерные пороги один раз при пересечении; polling/reconnect не повторяют их каждую секунду. Fallback и обновления DOM входят в приёмку; ручная проверка фактической речи исключена решением пользователя выше.

## 20. Нефункциональные требования

### 20.1. Производительность

- Каталог не выполняет отдельный запрос на каждую карточку.
- Проверка доступного контента агрегируется на уровне репозитория или заранее рассчитанной диагностики.
- Создание раундов выполняется одной транзакцией и пакетной вставкой, где это поддерживается текущим JPA-слоем.
- Индексы нужны по статусу/банку/аудитории контента, коду комнаты, статусу и `expires_at` комнаты.
- Страница комнаты остаётся работоспособной без WebSocket через polling.

### 20.2. Надёжность и конкуренция

- Вход участника и проверка вместимости выполняются под блокировкой комнаты.
- Старт идемпотентен.
- Ответ уникален для пары «раунд + участник».
- Фоновый тайм-аут и пользовательский ответ безопасно конкурируют через ограничение уникальности и повторную проверку времени.
- Незавершённое создание снимков откатывается полностью.
- После рестарта приложения активные комнаты продолжаются по сохранённым серверным временным меткам.

### 20.3. Наблюдаемость

Без добавления тяжёлой инфраструктуры первая версия должна писать структурированные сообщения о:

- создании, старте, завершении, отмене и истечении комнаты;
- отказе старта из-за контента;
- ошибке построения дистракторов;
- конфликте вместимости или повторном старте;
- автоматическом завершении по тайм-ауту.

В логах не сохраняются полные ответы ученика и секретные ключи ответа.

## 21. Совместимость с текущей реализацией

Текущие сущности `QuizRoom`, `QuizParticipant`, `QuizRound`, `QuizAnswer`, `QuizResult`, текущий WebSocket topic и серверный планировщик остаются основой.

Изменения должны быть добавочными:

1. Расширить статусы комнаты.
2. Добавить сущности игр и банков.
3. Добавить ссылку комнаты на версию игры.
4. Сделать источник раунда полиморфным через явный `content_kind` и типизированные внешние ключи.
5. Перенести формирование раундов с создания комнаты на атомарный старт.
6. Сохранить старый запрос создания предметной комнаты на переходный период.
7. Добавить новые поля в response без переименования старых.
8. Обновить клиентский текст, который сейчас обещает возможность менять ответ после сохранения.

Старые завершённые комнаты продолжают читаться через `question_version_id`. COMP-02 сохраняет legacy-renderer по закреплённой QuestionVersion; массового backfill нет. Старый рейтинг читается из сохранённых результатов в прежнем порядке score ↓, percent ↓, createdAt ↑; totalResponseMs=null, answered_at не превращается в длительность. На странице RU/KK поясняется отсутствие времени. Новые правила баллов/ничьей задним числом не применяются. Поиск существующих legacy-кодов сохраняет прежний trim/case-контракт. Исследование объёма/качества production-копии остаётся QA-06.

### 21.1. Два разных способа отключения

1. **Feature flag off на новой версии приложения.** Возвращает прежнюю точку входа в раздел, но новая версия продолжает обслуживать уже созданные новые комнаты/результаты, scheduler и административные данные. Этот штатный сценарий не требует отката БД.
2. **Возврат на предыдущую версию приложения.** Допускается только после проверки конкретного артефакта на мигрированной копии БД. Проверяются JPA/enum, все выборки и scheduler, nullable источники раундов, новый lifecycle, legacy create и история. Совместимость одних nullable-колонок недостаточна. Матрица допустимых состояний данных и безопасный операторский порядок фиксируются в `COMP-04`.

До записи новых комнат отдельно проверяется совместимость старого приложения с добавочной схемой и старыми данными. После записи новых типов/статусов откат на непроверенную старую версию запрещён; отключение флага не делает такие записи понятными старому коду. Рекомендуемая безопасная стратегия — flag off на текущем бинарном файле; бинарный откат только к проверенному совместимому артефакту. Если его нет, применяется исправленная новая версия, а не удаление новых комнат или destructive down-migration. Окончательный operational runbook утверждается в `ARCH-01`, проверяется в `QA-07` до релиза.

## 23. План тестирования

Существующий `QuizArenaIntegrationTest` не удаляется. Его сценарии сохраняются и адаптируются к опубликованной предметной игре.

### 23.1. Модульные тесты

- разрешение `grade_selection_mode` и `audience_policy`;
- валидация конфигурации каждого типа игры;
- построение дистракторов с альтернативными переводами и исключениями;
- проверка ответов `QUESTION`, `VOCABULARY`, `FACT`;
- сортировка результатов и разрешение ничьей;
- локализация карточек с определённым fallback;
- нормализация слов и кода комнаты;
- публикационный чек-лист.
- полный лимит времени для раннего явного пропуска и timeout; `false` не пропуск;
- независимость опубликованности, административной видимости и доступности ученику.

### 23.2. Репозиторные тесты

- выбираются только опубликованные версии;
- фильтрация по классу не пропускает взрослый/неразрешённый контент;
- универсальный контент не трактуется через пустой список классов;
- одна версия материала не повторяется внутри комнаты;
- индексы и уникальные ограничения работают;
- опубликованную используемую версию нельзя физически удалить.

### 23.3. Интеграционные игровые сценарии

1. Ученик создаёт словарную комнату и запускает её один.
2. Организатор приглашает второго ученика, тот отмечается готовым, оба играют одинаковые раунды.
3. Организатор не может стартовать с неготовым гостем.
4. Предметная игра требует разрешённый класс.
5. Игра «верю / не верю» стартует без класса.
6. Участник без класса не может играть в игру с `PARTICIPANT_GRADES`.
7. Недостаток контента не создаёт частичные раунды.
8. Два конкурентных старта создают один набор раундов.
9. Два конкурентных ответа фиксируют один результат.
10. Ответ после дедлайна отклоняется, тайм-аут фиксирует пропуск.
11. Ключи ответа не раскрываются до результата.
12. Будущие вопросы и варианты не раскрываются до начала своего раунда.
13. Изменение/архивирование банка после старта не меняет снимок комнаты.
14. Посторонний ученик и родитель не читают комнату и не отвечают.
15. Гость покидает ожидающую комнату; организатор отменяет её.
16. Ожидающая комната становится `EXPIRED`.
17. Перезапуск приложения не сбивает время активной комнаты.

### 23.4. MVC и интерфейс

- все формы содержат CSRF;
- каталог, пустое состояние и заблокированная карточка;
- ошибки кода комнаты;
- состояния `WAITING`, `ACTIVE`, `FINISHED`, `CANCELLED`, `EXPIRED`;
- мобильная ширина 360 px и десктоп;
- клавиатурная навигация;
- отсутствие скрытого ключа ответа в HTML и JSON;
- WebSocket-обновление и fallback polling;
- двойной клик по созданию и старту.
- регистр/пробелы кода, искусственная коллизия генератора и ограниченный retry без частичного создания;
- WebSocket-подписка постороннего/родителя, wildcard/SEND, отзыв после leave во всех вкладках;
- фокус после ответа/смены раунда, `aria-describedby`, однократные объявления порогов таймера;
- fallback для неполных исторических метаданных без обхода публикационной проверки;
- скрытие карточки, прямой POST, повтор и существующая WAITING-комната по согласованному `DEC-05`.

### 23.5. Миграционные тесты

- Flyway проходит на пустой базе;
- Flyway проходит на базе с текущими `quiz_rooms` и историческими результатами;
- текущие предметные комнаты остаются читаемыми;
- откат приложения на предыдущую версию рассматривается до включения флага: добавочные nullable-поля не должны мешать старому коду.
- проверяется конкретный старый артефакт до и после появления новых комнат/статусов; неподдерживаемые состояния исключают бинарный rollback, а не маскируются flag off;
- после отключения флага текущая версия продолжает новые ACTIVE/WAITING и чтение результатов без потери данных.

## 24. Критерии приёмки MVP

Функция готова к включению ученикам, когда одновременно выполнено следующее:

- [ ] Администратор может создать, проверить и опубликовать игру каждого из трёх типов.
- [ ] Опубликованная игра появляется в каталоге без изменения кода.
- [ ] Ученик начинает любую доступную игру максимум за два обязательных действия после входа в раздел.
- [ ] Одна и та же игра работает в комнате с одним и несколькими участниками.
- [ ] В комнате с одним участником нет искусственного требования ждать второго.
- [ ] В комнате с гостями старт заблокирован до их готовности.
- [ ] Игра без класса не показывает лишний выбор класса.
- [ ] Игра с классом не допускает контент другого класса.
- [ ] Ни один словарный вопрос не строится из неопубликованных или неподходящих материалов.
- [ ] Снимок раундов не изменяется после редактирования банка.
- [ ] Таймер и результат определяет сервер.
- [ ] До результата правильные ответы не раскрываются.
- [ ] Комната корректно восстанавливается после обновления страницы.
- [ ] Набор интеграционных тестов покрывает одиночный, совместный и тайм-аутный сценарии.
- [ ] Новый интерфейс визуально использует текущие компоненты и сетку проекта.
- [ ] Конфигурационный флаг позволяет вернуть текущий раздел без отката миграций.

3. Count/seconds default фиксированы; изменяются только флагами версии и внутри диапазона. Изменение настроек сбрасывает ready гостей и защищено revision (`DEC-01`, `ARCH-01`).

Спецификация сверена с текущими сущностями, миграцией комнат, API, ролями, клиентским таймером и HTML-макетами. Ниже перечислены обнаруженные расхождения, которые учтены в целевом решении.

| Текущее состояние | Требуемое изменение |
| --- | --- |
| `CreateQuizRoomRequest` требует `subjectId` и `gradeId` | Новая комната создаётся по `gameCode`; предмет и класс условны |

| Текущий API и тесты защищают комнаты по роли/участию | Сохранить эти гарантии и расширить новыми сценариями |

## 27. Решения, которые нельзя менять молча при реализации

Если разработка требует отступить от пунктов ниже, изменение сначала вносится в эту спецификацию и проходит ревью:

- комната существует и для одиночной игры;

- раунды получают неизменяемый снимок при старте;
- ключ ответа не отдаётся до завершения;
- сервер является источником времени, результата и прав доступа;
- новый интерфейс строится на текущей верстке проекта.

### 29.13. Definition of Done для любой кодовой задачи

Задача может получить `DONE`, когда:

- реализован её измеримый результат из таблицы;
- сохранена обратная совместимость, если задача явно не меняет утверждённый контракт;
- добавлены или обновлены тесты пропорционально риску;
- относящиеся тесты успешно запущены через Gradle;
- нет утечки правильных ответов, обхода роли или зависимости таймера от клиента;
- изменённые страницы проверены на узкой и широкой ширине;
- нет новых неописанных таблиц, JSON-полей или статусов;
- статус и подтверждение обновлены в этом разделе;
- выявленное отклонение от спецификации записано до передачи на ревью.

Для миграций дополнительно обязательны проверка существующей базы и отсутствие destructive-операций без отдельного плана. Для публикации контента дополнительно обязательны источник и исполняемая аудитория.
