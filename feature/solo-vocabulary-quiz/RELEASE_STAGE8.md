## До развёртывания

1. Указать целевой стенд, его конфигурацию и владельца переключения. Получить отдельную
   копию существующей БД и зафиксировать источник/дату, PostgreSQL version и размеры.
   Тестовый `quiz_test` содержит синтетические данные и не заменяет эту копию.
2. Использовать принятый пакет STARTER_CONTENT.md: существующая Математика,
   EN→RU, KK→RU и факты. Если есть иная публикация math/5/SCQ/1,
   импорт отказывает: требуется проверка существующего банка.
   Новые игры о животных — отдельный пакет ANIMAL_CONTENT.md.
   DRAFT basic-vocabulary не считать опубликованным seed. Речевой проход не является условием выпуска.
3. Выполнить QA-01..05 на окончательном коде. Собрать Gradle wrapper `build i18nVerify`,
   записать commit/локальный diff и SHA-256 именно собранного bootJar.
4. На отдельной копии выполнить QA-06: миграции до текущей версии, Flyway validate,
   Hibernate validate, сравнение прежних полей WAITING/ACTIVE/FINISHED, участников,
   вопросов/ответов/результатов. Проверить доступную историю с обеими локалями,
   legacy create/start и текущие активные игры. Записать время/блокировки миграций.
   V55 создаёт неуникальный `lower(code)` индекс PostgreSQL; измерить блокировку его
   transactional CREATE INDEX на реальном объёме. V1–V53 не менять; clean/repair/down не запускать.
5. QA-07 отдельно проверяет flag off текущего файла и бинарную совместимость согласно
   [ROLLBACK.md](ROLLBACK.md). Матрицы cb97aac на V53 и V55 относятся только к указанным там
   синтетическим схемам. Следующие миграции требуют повторной проверки; прежняя положительная
   ячейка не переносится автоматически на другую схему или копию.

   `QUIZ_GAME_CATALOG_ENABLED=false`. Записать hash, конфигурацию без секретов,
   Flyway version/validate, startup/health и доступ админки. Убедиться, что `/student/quiz`
   показывает legacy-вход, а существующие новые комнаты/результаты доступны по прямым ссылкам.
2. Опубликовать проверенный starter через обычный редакционный контракт с действительными
   ADMIN author/reviewer. `QuizStarterContentService.install(reviewerEmail)` — явная операция,
   не startup seed. Не публиковать демонстрационные/тестовые банки.
3. REL-02: на контролируемом стенде завершить минимум одну комнату каждого из трёх типов,
   solo и допустимый совместный состав, проверить время, false/skip, результаты и историю.
   Сохранить коды, участника-проверяющего, локали и времена проверки. Для тестового доступа

5. REL-04: наблюдать `quiz_event` create/start/finish/answers_timed_out и

   с проверяемыми комнатами; ответы, ключи, объяснения и аккаунты не журналировать.
   Проверить быстрое выключение флага текущего приложения, включая WAITING/ACTIVE/FINISHED.

   отсутствие развёртывания/включения оставлять явно открытым.

## Среда локальной QA

Только H2 в памяти либо `dlab-quiz-stage1-pg` с label `codex.task=quiz-games-stage1`,
актуальный loopback-порт из `docker port`. Синтетические схемы сохраняются.
`QUIZ_UI_SMOKE=1` допустим только для изолированной браузерной фикстуры;
в обычных прогонах переменная отсутствует. Команды и итоговые числа — VERIFY_STAGE1.md.

Локальный запуск actual bootJar: `scripts/quiz-preview.ps1`. Своя схема
`quiz_preview_*`, четыре случайных локальных аккаунта, strict-self-review=true,
AI/email/OAuth/push выключены, сервер только 127.0.0.1. Флаг на этом стенде
включается явно для пользовательского тестирования; default/production остаётся false.
Локальные REL-подтверждения — GAP § 14; общий статус IN_PROGRESS до QA-06/QA-07
и выпуска в предназначенном окружении.
