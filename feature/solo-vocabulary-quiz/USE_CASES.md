# Игровые викторины: use cases MVP

Дата: 2026-10-09. Основа: [спецификация v0.3](SPECIFICATION.md) и [HTML-макеты](flow/README.md).

Это перечень пользовательских целей и критериев приёмки, а не описание уже реализованной функции. При расхождении макета и спецификации действует спецификация. Открытые решения перечислены в [плане реализации](IMPLEMENTATION_PLAN.md); этот документ не закрывает их автоматически.

2026-10-09 пользователь явно принял пакет рекомендаций плана. Итоговые контракты закреплены в [ARCHITECTURE.md](ARCHITECTURE.md)/спеке; решение само по себе не означает реализованного сценария. Прогресс — в [GAP.md](GAP.md).

## 1. Границы и роли

- **Ученик** — пользователь с ролью `STUDENT`. Может стать организатором или гостем комнаты.
- **Организатор** — создавший комнату ученик; одновременно её участник, готов автоматически. Только он запускает и отменяет ожидающую игру.
- **Гость** — присоединившийся ученик; отдельно подтверждает готовность.
- **Администратор** — пользователь с ролью `ADMIN`, управляющий играми и банками. Автор и проверяющий — редакционные функции; необходимость разных людей требует решения, новые роли доступа здесь не вводятся.
- **Система** — сервер, управляющий временем, проверкой аудитории, снимками, тайм-аутами и результатом.

Родитель не получает право играть из-за связи с учеником. Знание кода не заменяет авторизацию и участие. Одиночная игра — обычная комната с одним участником, без отдельной модели solo-сессий.

MVP: три механики, комнаты на 1–4 участников, русский и казахский пользовательский интерфейс, курируемый контент. Не входят: поздний вход, команды, чат, SRS/«выученность», награды, аудио, генерация контента во время игры и ученический конструктор.

## 2. Портальная / пользовательская часть — 18 use cases

### P-01. Найти готовую игру в каталоге

**Актор:** ученик. **Условие:** авторизован, новый каталог включён.

**Сценарий:** открывает `/student/quiz`; видит опубликованные карточки с названием, механикой, описанием, длительностью/раундами, числом игроков и условием выбора класса; выбирает игру без обязательного дерева категорий.

**Результат и приёмка:** сортировка по административному порядку, затем названию; черновики и скрытые администратором карточки не видны. Публикация, административная видимость и доступность ученику независимы. При пустом каталоге показано объяснение. Отсутствующий нужный класс даёт заблокированную карточку с причиной/переходом в профиль — DEC-01 принят. Отсутствие обязательного перевода блокирует публикацию; fallback не заменяет проверку.

**Основа:** §§ 6.1, 9.1; `flow/index.html`, `flow/states.html`.

### P-02. Создать комнату выбранной игры

**Актор:** ученик, становящийся организатором. **Условие:** игра опубликована и доступна ученику.

**Сценарий:** нажимает карточку; сервер создаёт `WAITING`-комнату по `gameCode`, закрепляет опубликованную версию игры, создаёт уникальный код, добавляет организатора с `ready=true`; открывается экран комнаты.

**Результат и приёмка:** раунды ещё не созданы. Повтор одного запроса/двойной клик не создаёт второй комнаты. При конфликте уникальности кода сервер генерирует новый код и повторяет создание безопасно, без второй записи host; после ограниченного числа неудач возвращает безопасную ошибку без частичной комнаты. Настройки, банк и вместимость берутся из серверной версии игры, не из произвольных параметров клиента. Создание — POST с CSRF, даже если карточка выглядит ссылкой. Создание скрытой игры по прямому POST регулируется явно согласованным правилом A-19, а не только отсутствием карточки.

**Основа:** §§ 6.2, 9.2, 15; `flow/room.html`.

### P-03. Проверить и настроить игру перед стартом

**Актор:** организатор. **Условие:** комната `WAITING`.

**Сценарий:** читает правила, видит участников, готовность, число раундов и время; при PROFILE_DEFAULT проверяет/меняет разрешённый класс, при REQUIRED выбирает его, при NONE поля нет. Меняет число раундов/таймер только при явном разрешении версии, внутри диапазона; по умолчанию значения фиксированы.

**Результат и приёмка:** настройки валидированы сервером; несовместимая аудитория/нехватка контента объяснены до старта. Направление перевода, банк и вместимость не меняются учеником. Settings host-only в WAITING: revision, lock, повторная аудитория; изменение сбрасывает готовность гостей, host остаётся ready. Stale ready/settings и гонка со start не принимают устаревшие правила (ARCHITECTURE.md).

**Основа:** §§ 6.5, 8, 11.2, 25; `flow/room.html`.

### P-04. Запустить игру в одиночку

**Актор:** организатор. **Условие:** в ожидающей комнате только он, обязательные настройки заполнены.

**Сценарий:** нажимает «Начать игру»; сервер проверяет версию игры, аудиторию и достаточность контента, сохраняет все снимки и переводит комнату в `ACTIVE` одной транзакцией.

**Результат и приёмка:** не нужен второй игрок или дополнительное модальное подтверждение. Обязательный путь — два действия: карточка → начать. При ошибке комната остаётся `WAITING`, частичных раундов нет; запрос не уменьшает число вопросов и не расширяет аудиторию молча.

**Основа:** §§ 6.3, 9.3, 12.1; `flow/room.html`.

### P-05. Пригласить друзей

**Актор:** организатор. **Условие:** комната `WAITING`, есть свободные места.

**Сценарий:** нажимает «Пригласить», видит и копирует уже созданный код (и ссылку на вход, если она доступна), передаёт его другим ученикам; наблюдает присоединение и готовность гостей.

**Результат и приёмка:** приглашение необязательно для solo; код не генерируется повторно при раскрытии блока. Показ кода не предоставляет постороннему полный игровой state или ответы. Собственные чат и QR-сканер не требуются.

**Основа:** §§ 6.4, 9.4; `flow/room.html`.

### P-06. Найти комнату по коду и присоединиться

**Актор:** приглашённый ученик. **Условие:** авторизован как `STUDENT`.

**Сценарий:** вводит код; сервер удаляет пробелы по краям и приводит регистр к каноническому; ученик получает ограниченное превью игры и комнаты; подтверждает присоединение; сервер проверяет состояние, вместимость и аудиторию; добавляет гостя с `ready=false`.

**Результат и приёмка:** `qz7k2m` и ` QZ7K2M ` находят ту же комнату; внутренние пробелы/недопустимые символы не исправляются в чужой код автоматически. Нормализация едина в preview, join, комнатных HTTP-маршрутах и проверке WebSocket topic. Неизвестный код, заполненная, начатая, отменённая или истёкшая комната дают понятное сообщение. Повторный вход уже состоящего в комнате пользователя не создаёт дубля и восстанавливает его участие, в том числе после старта. Для нового участника поздний вход запрещён. Младший гость не входит в комнату более старшего класса; отсутствие нужного класса ведёт к исправлению профиля.

**Основа:** §§ 8, 9.5, 15, 18; `flow/join.html`.

### P-07. Подтвердить готовность к совместной игре

**Актор:** гость. **Условие:** присоединён к `WAITING`-комнате.

**Сценарий:** проверяет правила и нажимает «Готов»; сервер сохраняет готовность; участники видят обновление. Дальше гость ждёт организатора.

**Результат и приёмка:** повтор запроса безопасен. Гость не может запустить игру; организатор остаётся готов автоматически. Если хотя бы один присоединившийся гость не готов, запуск запрещён. Готовность не отменяет финальную проверку аудитории сервером.

**Основа:** §§ 6.4, 9.6, 16; гостевое состояние `flow/room.html`.

### P-08. Запустить совместную игру

**Актор:** организатор; гости — участники. **Условие:** 2–4 участника в пределах вместимости игры, все готовы.

**Сценарий:** организатор нажимает старт; сервер повторно проверяет окончательный состав и пересечение допустимой аудитории, формирует общие раунды и фиксирует время старта.

**Результат и приёмка:** все получают одинаковые снимки, порядок вопросов и вариантов. Гонка start/join не переполняет комнату и не включает непроверенного гостя. При нехватке безопасного контента старт не происходит. Следующие окна раундов определяются серверным расписанием, а не скоростью ответа одного игрока.

**Основа:** §§ 8, 9.6–9.7, 12, 20.2; `flow/room.html` и игровые страницы.

### P-09. Ответить в игре «Перевод слов»

**Актор:** участник. **Условие:** активен текущий словарный раунд.

**Сценарий:** читает слово; выбирает один из четырёх переводов; отправляет ответ; видит подтверждение принятия и ждёт следующего временного окна.

**Результат и приёмка:** один правильный перевод и три однозначных отвлекающих; направление фиксировано игрой (`en→ru`, `kk→ru` либо отдельный опубликованный `ru→kk`). Первый принятый ответ окончателен. До завершения всей игры нет подсветки правильного варианта, `isCorrect`, объяснения или ключа в ответе сервера/DOM.

**Основа:** §§ 7.1, 9.7, 12.2, 18; `flow/word-game.html` с исправлением демонстрационной обратной связи.

### P-10. Ответить в предметной викторине

**Актор:** участник. **Условие:** активен предметный раунд.

**Сценарий:** отвечает с помощью соответствующего виджета: один вариант `SCQ`, несколько `MCQ`, сопоставление `MATCHING`, заполнение `FILL_IN`; отправляет ответ.

**Результат и приёмка:** используются опубликованные `QuestionVersion`, существующая проверка предметных ответов и снимок конкретного запуска. Клиент видит только текущий раунд, не все будущие вопросы. Изменение банка не меняет уже созданный снимок; правильность раскрывается после `FINISHED`.

**Основа:** §§ 7.2, 12.3, 13.5; `flow/subject-game.html` (макет не покрывает все четыре виджета).

### P-11. Ответить в игре «Верю / не верю»

**Актор:** участник. **Условие:** активен раунд утверждения.

**Сценарий:** читает утверждение и выбирает «Верю» или «Не верю»; сервер принимает булево значение.

**Результат и приёмка:** `false` — полноценный ответ, не пропуск. Подписи локализуются независимо от протокола. Факт берётся из отдельного курируемого банка, а не фиктивного предмета. Объяснение и проверяемый источник доступны в итоговом разборе, не во время игры.

**Основа:** §§ 7.3, 12.4; `flow/true-false-game.html`.

### P-12. Пропустить вопрос или не успеть ответить

**Актор:** участник; при истечении времени — система. **Условие:** текущий раунд ещё не имеет принятого ответа участника.

**Сценарий:** ученик явно пропускает либо сервер закрывает окно по времени; фиксируется отсутствие ответа, начисляется ноль; по расписанию открывается следующий раунд.

**Результат и приёмка:** тайм-аут не перезаписывает принятый ответ. Идентичный retry идемпотентен, другой ответ конфликтует. Skip окончателен, даёт ноль и полный лимит для ничьей, как timeout; ранний skip не улучшает место. False — содержательный ответ. Payload: ID текущего раунда и либо typed answer, либо skipped=true. Клиент не продлевает время и не переходит вперёд; окно серверное `[start, end)` (ARCHITECTURE.md).

**Основа:** §§ 9.7, 13.6, 20.2; игровые страницы.

### P-13. Вернуться в игру после перезагрузки или потери связи

**Актор:** уже состоящий в комнате участник.

**Сценарий:** повторно открывает комнату тем же аккаунтом; клиент читает серверное состояние, восстанавливает актуальный раунд, факт принятия собственного ответа и оставшееся время. При недоступном WebSocket использует HTTP polling.

**Результат и приёмка:** игра не ставится на паузу из-за закрытой вкладки; сервер продолжает таймер и фиксирует пропуски. Будущий текст и ключи не раскрываются. Если комната завершилась, открывается результат. Потерянный ответ не считается сохранённым без серверного подтверждения; безопасный повтор не создаёт дубля.

**Основа:** §§ 9.9, 16, 20.2; комната, игровые страницы, `flow/states.html`.

### P-14. Посмотреть результат и разобрать ответы

**Актор:** участник завершённой комнаты. **Условие:** `FINISHED`.

**Сценарий:** открывает результат; видит свой счёт, место, число правильных ответов, общее число раундов, процент и таблицу участников, затем личный разбор раундов с ответом, правильностью и объяснением; у фактов — источник.

**Результат и приёмка:** правильный ответ даёт один балл, без бонуса скорости. Ничья: баллы по убыванию, суммарное время ответа по возрастанию, затем время присоединения; явные пропуски и неотвеченные раунды учитываются полным лимитом. Разбор воспроизводится из снимков даже после редактирования/архивации банка. Посторонний по коду не получает результат.

**Основа:** §§ 9.8, 13.6, 18; `flow/result.html`.

### P-15. Сыграть ещё раз

**Актор:** ученик из результата. **Условие:** игра по-прежнему опубликована и доступна.

**Сценарий:** нажимает повтор игры; создаётся новая ожидающая комната по текущей опубликованной версии; ученик становится её организатором и может начать или пригласить друзей.

**Результат и приёмка:** старая комната и результат не перезаписываются; предыдущие гости не переносятся автоматически. При снятии игры из каталога повтор недоступен с объяснением. «Повторить только ошибки» из визуальной концепции не превращается автоматически в новый режим MVP.

**Основа:** §§ 9.8, 21; `flow/result.html`.

### P-16. Покинуть ожидающую комнату

**Актор:** гость. **Условие:** комната `WAITING`.

**Сценарий:** нажимает выход; сервер удаляет его участие; остальные видят изменённый список и готовность.

**Результат и приёмка:** освобождается место, организатор может стартовать с оставшимися участниками, в том числе один. Выход гостя не отменяет всю комнату. После старта закрытие страницы не удаляет участие и не передаёт право старта другому человеку.

**Основа:** §§ 9.9, 10; `flow/room.html`.

### P-17. Отменить ожидающую игру

**Актор:** организатор. **Условие:** комната `WAITING`.

**Сценарий:** отменяет комнату; сервер переводит её в `CANCELLED`; гостям показывается состояние отмены с возвратом в каталог.

**Результат и приёмка:** дальнейший вход/старт запрещены. Гость не имеет этого права. Организатор не «выходит», оставляя бесхозную комнату; отмена не удаляет её физически. Из `ACTIVE` это действие не разрешено.

**Основа:** §§ 9.9, 10; полноценное состояние требует дополнения макета (`UX-03`).

### P-18. Узнать, что ожидание комнаты истекло

**Актор:** организатор/гость; переход выполняет система. **Условие:** ожидающая комната достигла `expires_at`.

**Сценарий:** сервер переводит комнату в `EXPIRED`; открытая вкладка или последующий переход по коду показывают истечение и путь к новому запуску.

**Результат и приёмка:** ожидание по умолчанию 30 минут, значение конфигурируется. Истёкшую комнату нельзя запустить/присоединить. Истечение и конкурентный старт имеют однозначный транзакционный результат; активная игра не истекает по правилу ожидания.

**Основа:** §§ 10, 17; полноценное состояние требует дополнения макета (`UX-03`).

## 3. Административная часть — 19 use cases

### A-01. Найти игру и оценить её состояние

**Актор:** администратор.

**Сценарий:** открывает список игр, фильтрует по поиску, типу, статусу, языку и ошибкам публикации; видит код, банк, доступный контент, обе политики, дату/автора; переходит к редактированию, диагностике или публикации.

**Результат и приёмка:** публикация и наличие нового черновика различимы. Счётчики вычисляются по данным, не перенесены из демонстрационного JS. Ученику административные маршруты недоступны.

**Основа:** § 11.1; `flow/admin-quizzes.html`.

### A-02. Создать черновик игры

**Актор:** администратор.

**Сценарий:** задаёт уникальный стабильный код и тип, названия/описания RU/KK, механику, порядок и разрешённый стиль карточки, значения и диапазоны раундов/таймера, вместимость 1–4; сохраняет черновик.

**Результат и приёмка:** `DRAFT` отсутствует в ученическом каталоге. Ошибки сохраняют введённые безопасные значения формы. Минимум участников всегда один; тип и код можно менять только до первой публикации. Конфигурация типизирована, произвольный JSON-конструктор не вводится.

**Основа:** §§ 11.2, 13.1; `flow/admin-quiz-edit.html` с исправлением лимитов.

### A-03. Подготовить новую редакцию опубликованной игры

**Актор:** администратор. **Условие:** есть опубликованная версия.

**Сценарий:** открывает редактирование, создаёт/изменяет новый черновик и сохраняет его; проходит проверку и повторную публикацию через A-07.

**Результат и приёмка:** текущая опубликованная версия продолжает работать до атомарной замены указателя. Код и тип после первой публикации неизменяемы. Уже созданные комнаты сохраняют свою версию игры, начатые — свои снимки. Сохранение черновика не равно публикации.

**Основа:** §§ 11.2, 13.1, 21; `flow/admin-quiz-edit.html`.

### A-04. Настроить выбор класса и безопасную аудиторию

**Актор:** администратор. **Условие:** редактируется черновик игры.

**Сценарий:** отдельно выбирает `grade_selection_mode` и `audience_policy`, задаёт разрешённые/фиксированные классы; проверяет совместимость настроек.

**Результат и приёмка:** `ROOM_GRADE` требует `PROFILE_DEFAULT`/`REQUIRED`; `PARTICIPANT_GRADES` не показывает поле класса и учитывает всех игроков. `UNIVERSAL` означает явную редакционную проверку, не пустой список классов. Возраст из макета не используется как автоматический фильтр: в профиле есть только класс.

**Основа:** § 8; в `flow/admin-quiz-edit.html` пока нет двух отдельных полей (`UX-03`).

### A-05. Связать игру с источником контента

**Актор:** администратор.

**Сценарий:** для слов выбирает набор и фиксированную языковую пару; для предметной игры — существующий предметный банк, классы, язык, сложность и допустимые типы; для фактов — отдельный набор утверждений.

**Результат и приёмка:** нельзя смешать источники разных типов или опубликовать ссылку на неподходящий банк. Предметные вопросы не копируются в новый банк. Межнаборные дистракторы выключены по умолчанию и включаются явно. Факты не оформляются как предметные `SCQ`.

**Основа:** §§ 7, 11.3, 12; `flow/admin-quiz-content.html`.

### A-06. Проверить, достаточно ли качественного контента

**Актор:** администратор. **Условие:** игра связана с банком.

**Сценарий:** открывает диагностику; видит всего опубликованных материалов, подходящих аудитории, реально пригодных к игре и исключённых; переходит к проблемным записям.

**Результат и приёмка:** показаны причины: непроверенность, неподходящие классы/язык, отсутствие переводов/источника, неоднозначность и нехватка дистракторов. Различается достаточность для минимума и для максимального разрешённого числа раундов; результат нельзя заменить числом всех записей банка. Финальная проверка при старте всё равно обязательна.

**Основа:** §§ 11.3, 11.7, 12; `flow/admin-quiz-content.html`.

### A-07. Проверить и опубликовать игру

**Актор:** администратор в функции автора/проверяющего согласно согласованной политике.

**Сценарий:** передаёт редакцию на проверку, утверждает; открывает checklist и ученический предпросмотр; исправляет ошибки; подтверждает предупреждения; публикует неизменяемую версию.

**Результат и приёмка:** ошибки блокируют серверную публикацию, даже если обойти кнопку. Проверяются локализации, лимиты, аудитория, опубликованность/проверенность источника и достаточность пригодного контента. Указатель опубликованной версии меняется атомарно; сохраняется аудит. Предпросмотр не создаёт скрыто реальную ученическую комнату.

**Основа:** §§ 11.6–11.7, 13.1; `flow/admin-quiz-publish.html`.

### A-08. Архивировать игру, сохранив историю

**Актор:** администратор. **Условие:** игра больше не должна предлагаться для новых запусков.

**Сценарий:** архивирует игру; она исключается из каталога и создания новых комнат.

**Результат и приёмка:** завершённые результаты и активные снимки не исчезают. Физического удаления в MVP нет. Archive блокирует новый start, прежняя WAITING остаётся с объяснением до cancel/expiry; автоматической замены игры/банка нет. Hide не archive и сам по себе старт прежней WAITING не блокирует (ARCHITECTURE.md).

**Основа:** §§ 11.6, 21, 25; отдельное действие/состояние макета нужно уточнить.

### A-09. Создать и организовать словарный набор

**Актор:** администратор.

**Сценарий:** создаёт набор с названием, направлением перевода и источником; работает с его редакцией, списком слов, статусами и фильтрами; задаёт разрешение межнаборных дистракторов, если оно нужно.

**Результат и приёмка:** `en→ru`, `kk→ru` и `ru→kk` — отдельные опубликованные направления. Есть версия набора и аудит изменений; обратный перевод не возникает автоматически из прямого. Набор без пригодного опубликованного наполнения не считается готовым источником игры.

**Основа:** §§ 7.1, 11.4, 13.2; `flow/admin-word-bank.html` (форма набора требует детализации).

### A-10. Создать или изменить учебное значение слова

**Актор:** администратор.

**Сценарий:** вводит исходное слово, произношение, часть речи, один основной и допустимые альтернативные переводы, примечание, сложность 1–5, источник, классы/универсальность; сохраняет редакцию.

**Результат и приёмка:** разные учебные значения многозначного слова — разные записи. Отображаемый текст сохраняется, нормализованное значение используется для проверок. У опубликованной записи изменение создаёт новую версию; нельзя заменить исторический смысл. Альтернативы исключают двусмысленные дистракторы, а не создают несколько правильных кнопок.

**Основа:** §§ 11.4, 12.2, 13.2; `flow/admin-word-edit.html`.

### A-11. Проверить дубли перед добавлением слова

**Актор:** администратор.

**Сценарий:** ищет по исходному слову/переводу; система предлагает похожие нормализованные записи; редактор открывает существующее значение либо создаёт действительно другое.

**Результат и приёмка:** регистр и лишние пробелы не скрывают вероятные дубли. Совпадение написания не запрещает отдельное значение автоматически; разные смыслы/языковые пары сохраняются. Дубликаты переводов внутри одной версии проверяются отдельно от поиска похожих слов.

**Основа:** § 11.4; банк и форма слова.

### A-12. Отправить слова на проверку и проверить их

**Актор:** администратор как автор/проверяющий.

**Сценарий:** отправляет одну или несколько завершённых редакций из `DRAFT` в `NEEDS_REVIEW`; проверяющий проверяет значение, перевод, источник и аудиторию; переводит корректную редакцию в `APPROVED`.

**Результат и приёмка:** сохраняются автор, проверяющий и история статусов. Только отправка на проверку не делает слово доступным ученикам. Ограничение самопроверки применяется согласно решению ревью. Для исправлений сохраняется управляемый черновик, без редактирования опубликованной версии на месте.

**Основа:** §§ 11.4, 11.6; `flow/admin-word-bank.html`, `flow/admin-word-edit.html`.

### A-13. Опубликовать слова и словарный набор

**Актор:** администратор. **Условие:** редакционные проверки пройдены.

**Сценарий:** публикует проверенные версии слов и редакцию набора; система валидирует обязательные поля, один основной перевод и аудиторию; обновляет доступность в диагностике игр.

**Результат и приёмка:** движок использует только опубликованный набор и опубликованные версии слов. Отдельно определяется пригодность для четырёх вариантов; статус публикации не подменяет проверку дистракторов. Новая публикация не меняет снимки ранее начатых комнат.

**Основа:** §§ 11.6, 12.2, 13.2; банк и форма слова.

### A-14. Исключить неоднозначные дистракторы

**Актор:** администратор.

**Сценарий:** проверяет предлагаемые неверные переводы; запрещает синонимичную/двусмысленную пару; при необходимости явно разрешает подбор из другого совместимого набора; повторяет диагностику.

**Результат и приёмка:** основной и альтернативные правильные переводы не используются как неверные ответы. Учитываются направление, публикация, аудитория и редакционные исключения; предпочтительны близкие часть речи/сложность. Нельзя создать пригодный раунд, если после фильтра остаётся меньше трёх дистракторов. Интерфейс управления исключениями ещё нужно детализировать.

**Основа:** §§ 12.2, 13.2; диагностика контента и словарный банк.

### A-15. Архивировать слово или словарный набор

**Актор:** администратор.

**Сценарий:** архивирует устаревшую запись/набор; они перестают участвовать в новых выборках; диагностика связанных игр обновляется.

**Результат и приёмка:** существующие снимки и результаты остаются читаемыми. Если безопасного контента стало недостаточно, новый старт блокируется с точными числами, а не использует архивные записи или случайный банк. Массовые редакционные действия не обходят валидацию отдельных записей.

**Основа:** §§ 11.4, 11.6, 12.1, 21; `flow/admin-word-bank.html`.

### A-16. Создать набор и редакцию утверждения

**Актор:** администратор.

**Сценарий:** открывает отдельный банк фактов, создаёт/выбирает набор; вводит текст RU/KK, истинность, объяснение, проверяемый источник и допустимые классы/универсальность; сохраняет черновик.

**Результат и приёмка:** булево значение отдельно от локализованных подписей. URL без содержательного объяснения не достаточен для публикации. При изменении опубликованного факта создаётся новая версия; предметный банк не используется как обход отсутствующей модели.

**Основа:** §§ 7.3, 11.5, 13.3; отдельные макеты банка/формы факта отсутствуют (`UX-03`).

### A-17. Проверить и опубликовать утверждение

**Актор:** администратор как автор/проверяющий.

**Сценарий:** отправляет редакцию на проверку, проверяет истинность по источнику, объяснение, переводы и аудиторию; утверждает и публикует. Затем проверяет готовность связанной игры.

**Результат и приёмка:** действует редакционный lifecycle `DRAFT → NEEDS_REVIEW → APPROVED → PUBLISHED`; сохраняется аудит. Неподтверждённый факт не попадает в игру. Объяснение/источник сохраняются в снимке при старте; версия после публикации неизменяема.

**Основа:** §§ 11.5–11.7, 12.4; новые административные макеты (`UX-03`).

### A-18. Архивировать утверждение или набор фактов

**Актор:** администратор.

**Сценарий:** снимает устаревший/ошибочный материал из новых выборок через архивирование, проверяет диагностику затронутых игр.

**Результат и приёмка:** факт не используется в новых раундах, но результаты прошлых комнат воспроизводимы. Для исправления создаётся новая проверенная редакция; история не переписывается. Автоматическое удаление материалов/комнат не вводится без отдельной политики хранения.

**Основа:** §§ 11.6, 12.4, 21, 25; новые административные макеты (`UX-03`).

### A-19. Управлять видимостью опубликованной игры

**Актор:** администратор. **Условие:** существует опубликованная игра; действие не является архивированием.

**Сценарий:** скрывает карточку из каталога или возвращает её; видит отдельно редакционный статус, опубликованную версию и административную видимость; изменение и автор записываются в аудит.

**Результат и приёмка:** скрытие не уничтожает опубликованную версию, не переписывает историю и не прерывает активные игры. DEC-05 принят: скрытие запрещает новые комнаты, включая прямой POST и повтор; прежняя WAITING-комната сохраняет join/start при остальных финальных проверках. HTTP и каталог применяют одно правило; возврат карточки не требует новой редакции контента. Архивация отдельно блокирует start. Поле видимости и audit принадлежат стабильной игре.

**Основа:** §§ 6.1, 11.2, 25; отдельное действие и состояния админки/повтора включены в `UX-03`, реализация — `GAME-09`.

## 4. Общие критерии для всех сценариев

1. Сервер проверяет роль, участие, полномочия организатора, статус комнаты и временное окно; клиентская кнопка не является защитой.
2. Выбор класса и допустимость материала независимы. Неизвестная аудитория не считается универсальной; нехватка контента не разрешает обход правил.
3. До `FINISHED` ключи, правильность и объяснения отсутствуют в HTTP, WebSocket, HTML и доступных клиенту снимках; будущие вопросы не выдаются заранее.
4. Тексты ошибок локализованы и предлагают безопасный следующий шаг. Серверный текст/HTML контента обрабатывается по существующим правилам экранирования и очистки.
5. Изменяющие запросы защищены CSRF; повтор/гонка не дублируют комнаты, участников, раунды и ответы.
6. WebSocket сообщает изменение, HTTP возвращает актуальное состояние; polling с интервалом 3 секунды обеспечивает работу без сокета. Подписка доступна только аутентифицированному STUDENT — действующему участнику соответствующей комнаты. После выхода гостя отзыв затрагивает все его открытые вкладки/подписки; последующие события не доставляются. Повторное соединение проходит проверку заново; угадывание topic не даёт доступа.
7. RU/KK, клавиатура, видимый фокус, читаемые статусы/ошибки, интерфейс на ширине 360 px, цели касания от 44×44 CSS px и reduced motion. После отправки фокус на статусе ответа, после смены раунда — на заголовке вопроса; ошибка связана с полем через `aria-describedby` и не обозначена только цветом. Таймер текстовый; live region обновляется при пересечении порогов, например 10 и 5 секунд, не каждую секунду/poll. По решению пользователя 2026-10-11 ручной речевой проход скринридером исключён из обязательной приёмки; факт проверки речи не заявляется.
8. История неизменяема; опубликованные версии и снимки не удаляются ради редактирования. При выключении нового каталога старые и новые уже созданные комнаты/результаты продолжают обслуживаться текущей версией приложения. Это не обещание безопасного отката на старый бинарный файл: его условия отдельно проверяются в `COMP-04`.
9. Fallback по принятому DEC-06: пользовательская locale → RU → другая доступная, blank отсутствует; обязательного заголовка нет нигде — безопасная недоступность + admin diagnosis. Обязательные RU/KK-поля публикации не заменяются, другой учебный источник/направление не выбирается. SSR/JSON согласованы; все ветки fallback тестируются.
