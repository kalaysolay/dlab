# Механизм тестирования

Документ описывает фактическое поведение основного модуля **Testing Hub** (страницы `/student/tests` и API `/api/test-sessions`) на текущий момент. Отдельно в конце описан `Quiz Arena`: он использует тот же банк вопросов, но собирает набор иначе.

## Что может попасть в тест

Источник — банк вопросов, а именно **текущая версия** (`questions.current_version_id`) вопроса. Версия допускается в пул, только если одновременно выполняются условия:

- родительский вопрос имеет статус `PUBLISHED`;
- версия относится к выбранному предмету;
- у версии есть связь с выбранным классом в `question_version_grades`;
- если в запросе передана сложность, она в точности совпадает с `question_versions.difficulty`.

Язык не участвует в отборе: он определяет только то, будут ли показаны поля `bodyRu`/`bodyKk`, варианты и объяснения на русском или казахском. Отбираются все четыре поддерживаемых типа: `SCQ`, `MCQ`, `MATCHING`, `FILL_IN`.

Для `SUBJECT` после фильтрации применяется адаптивное ранжирование. Оно учитывает mastery темы/атомарного навыка, предыдущие попытки, недавние ошибки и повторы. Слабые навыки получают больший шанс попасть в тест, а сильные не исключаются полностью и периодически проверяются. Для остальных типов теста пока используется нейтральная случайная стратегия.

Приоритет mastery: показатель атомарного навыка, затем показатель основной темы, затем статус «не изучено», если истории нет.

## Алгоритм старта сессии

1. Ученик выбирает предмет, класс и язык. В пользовательском интерфейсе MVP доступен только тип `SUBJECT`; API принимает также перечисленные типы `MODO`, `SOR`, `SOCH`, `KAZAKH_LANGUAGE`.
2. Список в форме показывает только пары «предмет—класс», в которых опубликовано не меньше `damulab.testing.min-published-per-subject-grade` вопросов. Перед стартом пара проверяется повторно.
3. Сервис запрашивает все подходящие опубликованные версии, поэтому новые вопросы не выпадают из рассмотрения из-за прежнего лимита первых 500 записей.
4. Определяется размер теста: значение из запроса, если оно передано, иначе `default-question-count`; в обоих случаях оно ограничивается `max-question-count` и фактическим размером пула. Поэтому при нехватке вопросов сессия всё равно стартует, но с меньшим числом заданий.
5. Для каждого кандидата рассчитывается вес: `max(10, 100 - mastery)`. Для вопроса без mastery используется вес `60`. Первый показ получает `+15`, недавняя ошибка `+30`, давно не проверявшийся навык `+20`. Если версия была в последних сессиях, итоговый вес умножается на `0.2`.
6. Выполняется взвешенная случайная выборка без повторов. Мягкая квота `max-topic-share-percent` ограничивает долю одной темы; если банк однородный и тест иначе не заполнить, квота снимается.
7. Выбранные версии фиксируются в `test_session_questions` с порядковыми номерами и ценой `1` балл. Уникальное ограничение БД не даёт одной версии попасть в одну сессию дважды.
8. В `test_sessions.settings_json` сохраняются итоговое число вопросов, стратегия и разбивка `weak/watch/unseen/strong`. Набор закреплён за сессией: дальнейшее редактирование или публикация вопросов не меняют уже начатый тест.

Если по паре предмет—класс достигнут минимальный порог, но после фильтра по запрошенной сложности пул пуст, старт вернёт `published_questions_not_found`.

## Ход теста и результат

Активная сессия отдаёт ученику текст, варианты и служебные идентификаторы, но не `answer_key_json`. Ответ можно сохранять и заменять до завершения. При `finish` для каждого вопроса сервер:

1. Берёт последний сохранённый ответ; отсутствие ответа считается пустым JSON `{}`.
2. Сверяет его с ключом ответа через `AnswerChecker`.
3. Создаёт `answer_evaluations` и начисляет либо полный балл (`1`), либо `0`: частичных баллов сейчас нет.
4. Сохраняет один `test_results`, переводит сессию в `FINISHED`, обновляет mastery/аналитику и активность для достижений.

Повторный `finish` идемпотентен: возвращается уже созданный результат.

Правила проверки:

- `SCQ` — выбран ровно один вариант и он равен правильному;
- `MCQ` — множество выбранных вариантов должно в точности совпасть с ключом;
- `MATCHING` — должны совпасть все пары;
- `FILL_IN` — должны пройти все поля по своему режиму: точное совпадение, нормализованный текст, число с допуском или регулярное выражение.

`time_limit_seconds` выводится как таймер в браузере, однако текущий сервер не отклоняет ответы и завершение по истечении времени. Это визуальный таймер, а не серверно принудительное ограничение.

## Конфигурация и данные

| Где | Что хранится | Как используется |
| --- | --- | --- |
| `src/main/resources/application.yml` → `damulab.testing` | `default-question-count: 12`, `max-question-count: 20`, `min-published-per-subject-grade: 1` | Размер теста по умолчанию, верхняя граница и порог доступности пары предмет—класс. |
| Там же | `selection-strategy: adaptive` | `ADAPTIVE` включает персональный подбор для `SUBJECT`; `RANDOM` служит быстрым откатом. |
| Там же | `recent-session-window: 3` | Количество последних сессий, вопросы из которых штрафуются как недавний повтор. Значение ограничивается диапазоном 0–10. |
| Там же | `max-topic-share-percent: 40` | Мягкая верхняя доля одной темы в наборе. |
| Там же | `mastery-stale-after-days: 30` | После этого срока навык получает бонус повторной проверки. |
| `src/main/resources/application-test.yml` → `damulab.testing` | Те же значения для интеграционных тестов | Переопределяет настройки при профиле `test`. |
| `src/main/java/kz/damulab/config/DamulabTestingProperties.java` | Java-привязка ключей YAML | Поставляет значения сервисам тестирования и адаптивному селектору. |
| `src/main/resources/db/migration/V7__testing_hub.sql` → `test_templates` | Шаблон `subject-slice`: `SUBJECT`, 10 вопросов, 1500 секунд | Из шаблона сейчас читается только `time_limit_seconds`. `default_question_count` шаблона в подборе **не используется**; число вопросов берётся из YAML/API. |
| Таблицы банка вопросов: `questions`, `question_versions`, `question_version_grades` | Статус вопроса, текущая версия, предмет, класс, сложность, варианты и ключ | Это фактические данные для фильтрации и проверки. |
| `skill_mastery` | Mastery ученика по теме и атомарному навыку, число попыток и дата последней проверки | Определяет базовый вес кандидата и устаревание знания. |
| Таблицы сессии: `test_sessions`, `test_session_questions`, `student_answers`, `answer_evaluations`, `test_results` | Снимок набора, ответы, оценка и итог | Хранят историю конкретной попытки. |

## Где искать код

- Отбор и создание сессии: `src/main/java/kz/damulab/testing/TestingHubService.java` (`startSession`).
- Расчёт весов и выборка: `src/main/java/kz/damulab/testing/AdaptiveQuestionSelector.java`.
- Доступность предметов и классов: `src/main/java/kz/damulab/testing/TestStartAvailabilityService.java`.
- SQL-фильтр опубликованных вопросов: `src/main/java/kz/damulab/questions/QuestionVersionRepository.java` (`findPublishedForTest`).
- Проверка ответов: `src/main/java/kz/damulab/testing/AnswerChecker.java`.
- HTTP API: `src/main/java/kz/damulab/testing/TestingHubApiController.java`.

## Отличие Quiz Arena

`Quiz Arena` создаёт комнату для 2–4 участников. Его параметры (`questionCount` 1–12, `roundSeconds` 5–120, `maxPlayers` 2–4) приходят в `CreateQuizRoomRequest`; значения по умолчанию `5`, `20`, `4` находятся непосредственно в `QuizService`, а не в `damulab.testing`.

Для комнаты выполняется тот же фильтр опубликованных текущих версий по предмету, классу и необязательной сложности, но случайного перемешивания нет: сервис берёт первые `questionCount` записей в порядке `createdAt ASC`. Затем создаются `quiz_rounds`; каждый раунд имеет серверное временное окно и при пропуске получает нулевой ответ. Планировщик таймаутов настраивается ключами `damulab.quiz.timeout-worker-*`; в `application-test.yml` он выключен.

Подробный контракт комнаты приведён в [QUIZ_ARENA.md](QUIZ_ARENA.md), а API Testing Hub — в [TESTING_HUB_API.md](TESTING_HUB_API.md).
